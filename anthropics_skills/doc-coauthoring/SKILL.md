# 文档协作编写工作流

此技能提供引导用户完成协作文档创建的结构化工作流。作为主动引导者，引导用户完成三个阶段：上下文收集、完善与结构、读者测试。

## 何时提供此工作流

**触发条件:**
- 用户提到编写文档："write a doc"、"draft a proposal"、"create a spec"、"write up"
- 用户提到特定文档类型："PRD"、"design doc"、"decision doc"、"RFC"
- 用户似乎正在开始一个重要的写作任务

**初始提供:**
向用户提供用于协作编写文档的结构化工作流。解释三个阶段：

1. **上下文收集**：用户提供所有相关上下文，同时 Claude 提出澄清问题
2. **完善与结构**：通过头脑风暴和编辑迭代构建每个部分
3. **读者测试**：用全新的 Claude（无上下文）测试文档，在其他人阅读之前发现盲点

解释这种方法有助于确保文档在其他人阅读时（包括当他们将其粘贴到 Claude 中时）效果良好。询问他们是尝试这种工作流还是更喜欢自由形式。

如果用户拒绝，自由形式工作。如果用户接受，进入第 1 阶段。

## 阶段 1：上下文收集

**目标**：弥合用户所知道的内容与 Claude 所知道的内容之间的差距，以便后续提供智能指导。

### 初始问题

首先询问用户关于文档的元上下文：

1. 这是什么类型的文档？（例如，技术规范、决策文档、提案）
2. 主要受众是谁？
3. 当有人阅读时，期望产生什么影响？
4. 是否有要遵循的模板或特定格式？
5. 还有哪些其他约束或需要了解的上下文？

告知他们可以用简写形式回答，或任何他们觉得方便的方式倾倒信息。

**如果用户提供了模板或提到了文档类型：**
- 询问他们是否有模板文档可以分享
- 如果他们提供了共享文档的链接，使用适当的集成来获取它
- 如果他们提供了文件，读取它

**如果用户提到编辑现有的共享文档：**
- 使用适当的集成来读取当前状态
- 检查图片是否有 alt-text
- 如果存在没有 alt-text 的图片，解释当其他人使用 Claude 理解文档时，Claude 将无法看到它们。询问他们是否要生成 alt-text。如果是，请求他们将每张图片粘贴到聊天中以生成描述性 alt-text。

### 信息倾倒

一旦初始问题得到回答，鼓励用户倾倒所有他们有过的上下文。请求以下信息：
- 项目/问题的背景
- 相关的团队讨论或共享文档
- 为什么替代方案未被使用
- 组织背景（团队动态、过去的事件、政治）
- 时间线压力或约束
- 技术架构或依赖项
- 利益相关者担忧

建议他们不要担心组织——只是全部倾倒出来。提供多种方式提供上下文：
- 信息倾倒式的随心所想
- 指向团队频道或线程阅读
- 链接到共享文档

**如果集成可用**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），提到这些可以用来直接拉入上下文。

**如果没有检测到集成且在 Claude.ai 或 Claude app 中：** 建议他们可以在 Claude 设置中启用连接器，以允许直接从消息应用和文档存储拉取上下文。

告知他们一旦完成初始倾倒，将提出问题。

**在上下文收集过程中：**

- 如果用户提到团队频道或共享文档：
  - 如果集成可用：告知他们内容现在将被读取，然后使用适当的集成
  - 如果集成不可用：解释缺少访问权限。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提到未知的实体/项目：
  - 询问是否应该搜索连接的工具以了解更多信息
  - 在搜索前等待用户确认

- 随着用户提供上下文，跟踪正在学习的内容和仍不清楚的内容

**提出澄清问题：**

当用户表示他们已经完成初始倾倒（或在提供了大量上下文之后），提出澄清问题以确保理解。

基于上下文中的空白生成 5-10 个编号问题。

告知他们可以用简写形式回答（例如"1：是，2：见 #频道，3：否因为向后兼容"），链接到更多文档，指向要阅读的频道，或只是继续信息倾倒。无论哪种方式对他们来说最有效。

**退出条件：**
当问题显示出理解时——当边缘情况和权衡可以在不需要解释基础知识的情况下被询问时，就已收集了足够的上下文。

**过渡：**
询问是否还有其他想在此阶段提供的上下文，或者是否该进入起草文档了。

如果用户想添加更多，让他们添加。当准备好时，进入第 2 阶段。

## 阶段 2：完善与结构

**目标**：通过头脑风暴、筛选和迭代完善，逐节构建文档。

**给用户的说明：**
解释文档将逐节构建。对于每个部分：
1. 将提出关于包含什么内容的澄清问题
2. 头脑风暴 5-20 个选项
3. 用户将表明哪些保留、删除、合并
4. 将起草该部分
5. 通过精确编辑进行完善

从最不确定的部分开始（通常是核心决策/提案），然后处理其余部分。

**部分排序：**

如果文档结构清晰：
询问他们想从哪个部分开始。

建议从最不确定的部分开始。对于决策文档，通常是核心提案。对于规范，通常是技术方法。概述部分最好留到最后。

如果用户不知道他们需要哪些部分：
基于文档类型和模板，建议 3-5 个适合该文档类型的章节。

询问这个结构是否合适，或者他们是否想要调整。

**一旦结构达成一致：**

使用占位符文本创建初始文档结构。

**如果可以使用 artifacts：**
使用 `create_file` 创建一个 artifact。这给了 Claude 和用户一个要工作的支架。

告知他们将创建所有章节的占位符的初始结构。

创建包含所有部分标题和简要占位符文本（如"[待编写]"或"[此处内容]"）的 artifact。

提供支架链接并表明是时候填充每个部分了。

**如果没有 artifacts：**
在工作目录中创建一个 markdown 文件。适当地命名它（例如 `decision-doc.md`、`technical-spec.md`）。

告知他们将创建包含所有章节占位符的初始结构。

创建带有所有章节标题和占位符文本的文件。

确认文件名已创建并表明是时候填充每个部分了。

**对于每个部分：**

### 步骤 1：澄清问题

宣布将在 [章节名称] 部分上开始工作。提出 5-10 个关于应该包含什么的澄清问题：

基于上下文和章节目的生成 5-10 个具体问题。

告知他们可以用简写形式回答，或只是表明什么是重要的覆盖。

### 步骤 2：头脑风暴

对于 [章节名称] 部分，头脑风暴 5-20 个可能包含的内容，取决于该部分的复杂性。寻找：
- 可能已被遗忘的共享上下文
- 尚未提及的角度或考虑因素

基于部分复杂性生成 5-20 个编号选项。在最后，如果他们想要更多选项，可以提出头脑风暴更多的选项。

### 步骤 3：筛选

询问哪些点应该保留、删除或合并。请求简要理由以帮助了解下一节的优先级。

提供示例：
- "保留 1,4,7,9"
- "删除 3（重复 1）"
- "删除 6（受众已经知道这个）"
- "合并 11 和 12"

**如果用户给出自由反馈**（例如"看起来不错"或"我大部分喜欢但…"）而不是编号选择，提取他们的偏好并继续。解析他们想要保留/删除/更改的内容并应用它。

### 步骤 4：空白检查

基于他们选择的内容，询问 [章节名称] 部分是否有任何重要的缺失内容。

### 步骤 5：起草

使用 `str_replace` 将此部分的占位符文本替换为实际起草的内容。

宣布将根据他们选择的内容现在起草 [章节名称] 部分。

**如果使用 artifacts：**
起草后，提供 artifact 的链接。

请他们通读并指出要更改的内容。注意，具体有助于了解他们未来的风格。

**如果使用文件（无 artifacts）：**
起草后，确认完成。

告知 [章节名称] 部分已在 [filename] 中起草。请他们通读并指出要更改的内容。注意，具体有助于了解他们未来的风格。

**给用户的关键说明（在起草第一部分时包括）：**
提供一个提示：不要直接编辑文档，指示他们指出要更改的内容。这有助于学习他们未来的风格。例如："删除 X 项目符号——已被 Y 涵盖"或"使第三段更简洁"。

### 步骤 6：迭代完善

随着用户提供反馈：
- 使用 `str_replace` 进行编辑（从不重印整个文档）
- **如果使用 artifacts**：每次编辑后提供 artifact 链接
- **如果使用文件**：只需确认编辑完成
- 如果用户直接编辑文档并请求读取： mentally 注意他们所做的更改，并记住它们以供将来的章节使用（这显示了他们的偏好）

**继续迭代**，直到用户对该部分满意。

### 质量检查

经过 3 次连续迭代而没有重大更改后，询问是否有什么可以在不丢失重要信息的情况下删除。

当部分完成时，确认 [章节名称] 已完成。询问是否准备好进入下一部分。

**对所有章节重复此过程。**

### 接近完成

当接近完成（80%+ 的章节完成）时，宣布意图重新阅读整个文档并检查：
- 各节之间的流程和一致性
- 冗余或矛盾
- 任何感觉像"马虎"或通用填充的内容
- 每个句子是否都有分量

阅读整个文档并提供反馈。

**当所有章节都起草和细化了：**
宣布所有章节都已起草。表明意图最后再审查一次整个文档。

审查整体连贯性、流程、完整性。

提供任何最终建议。

询问是转到读者测试，还是他们想再完善任何东西。

## 阶段 3：读者测试

**目标**：用全新的 Claude（无上下文泄漏）测试文档，以验证它对读者有效。

**给用户的说明：**
解释现在将进行测试，看看文档是否真的对读者有效。这发现盲点——对作者有意义但可能让其他人困惑的内容。

### 测试方法

**如果对子代理有访问权限（例如，在 Claude Code 中）：**

直接执行测试，无需用户参与。

#### 步骤 1：预测读者问题

宣布打算预测读者在试图发现此文档时会问什么问题。

生成 5-10 个读者会现实地问的问题。

#### 步骤 2：用子代理测试

宣布这些问题将用全新的 Claude 实例（没有此对话的上下文）进行测试。

对于每个问题，使用仅包含文档内容和问题的子代理。

总结读者 Claude 对每个问题是对了还是错了。

#### 步骤 3：运行其他检查

宣布将执行其他检查。

调用子代理检查模糊性、错误假设、矛盾。

总结发现的任何问题。

#### 步骤 4：报告和修复

如果发现的问题：
报告读者 Claude 在具体问题上遇到困难。

列出具体问题。

表明意图修复这些空白。

循环回到有问题的部分的完善。

---

**如果没有子代理访问权限（例如，claude.ai web 界面）：**

用户需要手动进行测试。

#### 步骤 1：预测读者问题

询问当人们试图发现此文档时会问什么问题。他们会输入什么问题到 Claude.ai？

生成 5-10 个读者会现实地问的问题。

#### 步骤 2：设置测试

提供测试说明：
1. 打开一个新的 Claude 对话：https://claude.ai
2. 粘贴或共享文档内容（如果使用启用了连接器的共享文档平台，提供链接）
3. 向读者 Claude 询问生成的问题

对于每个问题，指示读者 Claude 提供：
- 答案
- 是否有任何模糊或不清晰的内容
- 文档假设什么先验知识/上下文
- 是否有任何内部矛盾或不一致

检查读者 Claude 是否给出正确答案或误解任何内容。

#### 步骤 3：其他检查

还向读者 Claude 询问：
- "这个文档中可能有什么模糊或不清晰的内容？"
- "文档假设读者已经知道什么知识或上下文？"
- "是否有任何内部矛盾或不一致之处？"

#### 步骤 4：根据结果迭代

询问读者 Claude 错了什么或在哪里遇到困难。表明意图修复这些空白。

循环回到任何有问题部分的完善。

---

### 退出条件（两种方法）

当读者 Claude 持续正确回答问题且不出现新的空白或模糊之处时，文档就准备好了。

## 最终审查

当读者测试通过时：
宣布文档已通过读者 Claude 测试。完成前：

1. 建议他们自己做最后的通读——他们拥有此文档并对其质量负责
2. 建议再次检查任何事实、链接或技术细节
3. 请他们验证它是否达到了他们想要的影响

询问他们是否想要再审查一次，或者工作是否完成。

**如果用户想要最终审查，提供它。否则：**
宣布文档完成。提供一些最终提示：
- 考虑将此对话链接到附录中，以便读者可以看到文档是如何开发的
- 使用附录提供深度而不使主文档臃肿
- 根据真实读者的反馈更新文档

## 有效引导的技巧

**语气:**
- 直接且有程序性
- 当它影响用户行为时简要解释原理
- 不要试图"销售"这种方法——只是执行它

**处理偏差:**
- 如果用户想跳过阶段：询问他们是否想跳过并自由编写
- 如果用户似乎沮丧：承认这花费的时间比预期的长。建议加快的方法
- 总是给用户调整过程的自主权

**上下文管理:**
- 在整个过程中，如果缺少关于所提到内容的上下文，主动询问
- 不要让空白积累——在出现时就解决

**artifact 管理:**
- 使用 `create_file` 来起草完整的部分
- 使用 `str_replace` 进行所有编辑
- 每次更改后提供 artifact 链接
- 永远不要将 artifacts 用于头脑风暴列表——那只是对话

**质量重于速度:**
- 不要赶过阶段
- 每次迭代都应该有有意义的改进
- 目标是产生真正对读者有效的文档
