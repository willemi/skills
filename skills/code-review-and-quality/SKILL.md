# 代码审查与质量

## 概述

多维度代码审查与质量门禁。每次变更在合并前都必须经过审查——没有例外。审查涵盖五个维度：正确性、可读性、架构、安全性和性能。

**批准标准：** 当变更确实改善了整体代码健康状况时予以批准，即使它不是完美的。完美代码并不存在——目标是持续改进。不要仅仅因为代码不完全符合你的写法而阻止变更。如果它改善了代码库并遵循项目约定，就予以批准。

## 何时使用

- 在合并任何 PR 或变更之前
- 在完成功能实现之后
- 当其他代理或模型产出了你需要评估的代码时
- 在重构现有代码时
- 在任何错误修复之后（同时审查修复内容和回归测试）

## 五轴审查

每次审查都从这些维度评估代码：

### 1. 正确性

代码是否完成了它声称要做的事情？

- 是否符合规范或任务要求？
- 是否处理了边缘情况（null、空值、边界值）？
- 是否处理了错误路径（不仅仅是正常路径）？
- 是否通过了所有测试？测试是否真的测试了正确的内容？
- 是否存在差一错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

另一位工程师（或代理）能否在不需作者解释的情况下理解这段代码？

- 名称是否具有描述性且与项目约定一致？（避免无上下文的 `temp`、`data`、`result`）
- 控制流是否直接明了（避免嵌套的三元运算符、深层回调）？
- 代码是否逻辑组织（相关代码分组、清晰的模块边界）？
- 是否存在应该简化的"巧妙"技巧？
- **能否用更少的行数完成？**（1000 行可以用 100 行完成就是失败）
- **抽象是否值得其复杂度？**（不要为单次用例进行泛化）
- 注释是否有助于阐明非显而易见的意图？（但不要注释显而易见的代码。）
- 是否存在死代码残留：无操作变量（`_unused`）、向后兼容性垫片或 `// removed` 注释？

### 3. 架构

变更是否符合系统的设计？

- 是否遵循现有模式或引入了新模式？如果是新的，是否有正当理由？
- 是否保持了干净的模块边界？
- 是否存在应该共享的代码重复？
- 依赖关系是否流向正确方向（无循环依赖）？
- 抽象级别是否合适（既不过度设计，也不耦合过紧）？

### 4. 安全性

有关详细安全指南，请参阅 `security-and-hardening`。该变更是否引入了漏洞？

- 是否对用户输入进行了验证和清理？
- 是否将秘密保持在代码、日志和版本控制之外？
- 是否在需要的地方进行了身份验证/授权检查？
- SQL 查询是否参数化（无字符串拼接）？
- 输出是否编码以防止 XSS？
- 依赖来源是否可信且无已知漏洞？
- 是否将外部源（API、日志、用户内容、配置文件）的数据视为不可信？
- 在系统边界使用逻辑或渲染之前，是否验证了外部数据流？

### 5. 性能

有关详细性能分析和优化，请参阅 `performance-optimization`。该变更是否引入了性能问题？

- 是否存在 N+1 查询模式？
- 是否存在无限制循环或无约束的数据获取？
- 是否存在应该异步的同步操作？
- UI 组件中是否存在不必要的重新渲染？
- 列表端点是否缺少分页？
- 是否存在在热路径中创建的大型对象？

## 变更规模

小而聚焦的变更更容易审查、更快合并、更安全部署。目标规模：

```
~100 行变更   → 良好。一次坐席即可审查。
~300 行变更   → 如果它是单一逻辑变更则可接受。
~1000 行变更  → 太大。拆分它。
```

**什么是"一次变更"：** 一个自包含的修改，解决一件事，包含相关测试，在提交后保持系统功能。功能的一部分——不是整个功能。

**当变更太大时的拆分策略：**

| 策略 | 方法 | 时机 |
|----------|-----|------|
| **堆叠** | 提交小变更，基于它开始下一个 | 顺序依赖 |
| **按文件组** | 不同组的变更需要不同审查者 | 横切关注点 |
| **水平** | 先创建共享代码/存根，然后是消费者 | 分层架构 |
| **垂直** | 将功能拆分为更小的全栈切片 | 功能工作 |

**大变更何时可接受：** 完整的文件删除和自动化重构，此时审查者只需验证意图，而非每一行。

**将重构与功能工作分离。** 同时重构现有代码和添加新行为的变更是两次变更——分别提交。小的清理（变量重命名）可由审查者酌情包含。

## 变更描述

每次变更都需要一个在版本控制历史中独立存在的描述。

**第一行：** 简短、祈使、独立。"Delete the FizzBuzz RPC" 而非 "Deleting the FizzBuzz RPC." 必须信息丰富，使搜索历史的人无需阅读差异就能理解变更。

**正文：** 正在改变什么以及为什么。包括代码本身不明显的背景、决策和推理。在相关处链接错误编号、基准测试结果或设计文档。当存在方法不足时予以承认。

**反模式：** "Fix bug"、"Fix build"、"Add patch"、"Moving code from A to B"、"Phase 1"、"Add convenience functions."

## 审查流程

### 步骤 1：理解上下文

在看代码之前，理解意图：

```
- 这个变更试图完成什么？
- 它实现了什么规范或任务？
- 预期的行为变化是什么？
```

### 步骤 2：先审查测试

测试揭示意图和覆盖率：

```
- 变更是否有测试？
- 它们是测试行为（而非实现细节）吗？
- 边缘情况是否覆盖？
- 测试是否有描述性名称？
- 如果代码更改，测试是否捕获回归？
```

### 步骤 3：审查实现

带着五个维度走查代码：

```
对于每个变更的文件：
1. 正确性：这段代码是否做了测试所说的它应该做的？
2. 可读性：我能否不帮助就理解它？
3. 架构：它是否符合系统？
4. 安全性：有漏洞吗？
5. 性能：有瓶颈吗？
```

### 步骤 4：分类问题

为每条评论标注严重程度，以便作者知道什么是必需的 versus 可选的：

| 前缀 | 含义 | 作者操作 |
|--------|---------|---------------|
| *(无前缀)* | 必需的变更 | 必须在合并前解决 |
| **Critical:** | 阻止合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:** | 次要，可选 | 作者可以忽略——格式、样式偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑但非必需 |
| **FYI** | 仅信息性 | 无需操作——未来参考的上下文 |

这可以防止作者将所有反馈视为强制性的，在可选建议上浪费时间。

### 步骤 5：验证验证

检查作者的验证故事：

```
- 运行了哪些测试？
- 构建是否通过？
- 是否手动测试了变更？
- UI 变更是否有截图？
- 是否有前后对比？
```

## 多模型审查模式

为不同的审查视角使用不同的模型：

```
模型 A 编写代码
    │
    ▼
模型 B 审查正确性和架构
    │
    ▼
模型 A 处理反馈
    │
    ▼
人工做出最终决定
```

这捕获了单个模型可能遗漏的问题——不同的模型有不同的盲点。

**审查代理的示例提示：**
```
审查此代码变更的正确性、安全性和项目约定遵守情况。
规范说 [X]。变更应该 [Y]。
将问题标记为 Critical、Important 或 Suggestion。
```

## 死代码卫生

在任何重构或实现变更之后，检查孤立代码：

1. 识别现在无法访问或未使用的代码
2. 明确列出
3. **删除前询问：** "我应该移除这些现在未使用的元素吗：[列表]？"

不要留下死代码——它会让未来的读者和代理感到困惑。但不要默默地删除不确定的内容。如有疑问，请询问。

```
DEAD CODE IDENTIFIED:
- formatLegacyDate() in src/utils/date.ts — replaced by formatDate()
- OldTaskCard component in src/components/ — replaced by TaskCard
- LEGACY_API_URL constant in src/config.ts — no remaining references
→ Safe to remove these?
```

## 审查速度

缓慢的审查会阻塞整个团队。审查的上下文切换成本小于强加给他人的等待成本。

- **在一个工作日内回复** —— 这是最大值，不是目标
- **理想节奏：** 在审查请求到达后不久回复，除非深度专注编码。典型的变更应在一天内完成多个审查轮次
- **优先快速单独响应** 而非快速最终批准。快速反馈减少挫败感，即使需要多轮
- **大变更：** 要求作者拆分它们，而不是审查一个巨大的变更集

## 处理分歧

解决审查争议时，应用此层级：

1. **技术事实和数据** 优先于意见和偏好
2. **样式指南** 是样式问题的绝对权威
3. **软件设计** 必须基于工程原则评估，而非个人偏好
4. **代码库一致性** 如果不降低整体健康状况则可接受

**不要接受"我稍后会清理。"** 经验表明延迟的清理很少发生。要求提交前清理，除非是真正的紧急情况。如果周围问题无法在此变更中解决，要求创建带有自我分配的 bug。

## 审查中的诚实

审查代码时——无论是你写的、其他代理写的还是人工写的：

- **不要 rubber-stamp。** 没有审查证据的"LGTM"对任何人都无帮助。
- **不要弱化真正的问题。** 当这是一个会冲击生产的错误时说"这可能是个小问题"是不诚实的。
- **尽可能量化问题。** "这个 N+1 查询将为列表中的每个项目增加约 50ms" 比"这可能很慢"更好。
- **对有明确问题的方法提出异议。** 审查中的谄媚是失败模式。如果实现有问题，直接说出并提出替代方案。
- **优雅地接受覆盖。** 如果作者有完整上下文并不同意， defer 到他们的判断。评论代码，而非人——将人身批评重新表述为专注于代码本身。

## 依赖纪律

代码审查的一部分是依赖审查：

**在添加任何依赖之前：**
1. 现有栈是否能解决这个？（通常可以。）
2. 依赖有多大？（检查包影响。）
3. 它是否积极维护？（检查最后一次提交、开放问题。）
4. 是否有已知漏洞？（`npm audit`）
5. 许可证是什么？（必须与项目兼容。）

**规则：** 优先使用标准库和现有实用程序而非新依赖。每个依赖都是负债。

## 审查清单

```markdown
## 审查：[PR/变更标题]

### 上下文
- [ ] 我理解这个变更做什么以及为什么

### 正确性
- [ ] 变更符合规范/任务要求
- [ ] 边缘情况已处理
- [ ] 错误路径已处理
- [ ] 测试充分覆盖变更

### 可读性
- [ ] 名称清晰一致
- [ ] 逻辑直接
- [ ] 无不必要的复杂度

### 架构
- [ ] 遵循现有模式
- [ ] 无不必要的耦合或依赖
- [ ] 适当的抽象级别

### 安全性
- [ ] 代码中无秘密
- [ ] 边界输入已验证
- [ ] 无注入漏洞
- [ ] 已实施身份验证检查
- [ ] 外部数据源被视为不可信

### 性能
- [ ] 无 N+1 模式
- [ ] 无无限制操作
- [ ] 列表端点有分页

### 验证
- [ ] 测试通过
- [ ] 构建成功
- [ ] 已执行手动验证（如适用）

### 裁决
- [ ] **批准** — 可合并
- [ ] **请求变更** — 必须解决问题
```

## 常见合理化

| 合理化 | 现实 |
|---|---|
| "它能用，这就足够好" | 可工作但不可读、不安全或架构错误的代码创造了复利的债务。 |
| "我写了它，所以我知道它正确" | 作者对自己的假设是盲目的。每次变更都受益于另一双眼睛。 |
| "我们稍后会清理" | 以后永远不会来。审查就是质量门——使用它。要求提交前清理，而不是之后。 |
| "AI 生成的代码可能没问题" | AI 代码需要更多而非更少审查。它自信且 plausible，即使错了。 |
| "测试通过了，所以它很好" | 测试是必要的但不是充分的。它们不捕获架构问题、安全问题或可读性顾虑。 |

## 红旗

- 无任何审查就合并的 PR
- 仅检查测试是否通过的审查（忽略其他轴）
- 没有实际审查证据的"LGTM"
- 无安全重点审查的安全敏感变更
- 太大无法 properly 审查的大 PR（拆分它们）
- 无回归测试的错误修复 PR
- 无严重性标签的审查评论——不清楚什么是必需的 vs 可选的
- 接受"我稍后修复"——它永远不会发生

## 验证

审查完成后：

- [ ] 所有 Critical 问题已解决
- [ ] 所有 Important 问题已解决或明确推迟并附带理由
- [ ] 测试通过
- [ ] 构建成功
- [ ] 验证故事已记录（什么改变了，如何验证的）
